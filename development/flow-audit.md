# 业务闭环审计结论（flow-audit）

> 审计日期：2026-08-20
> 范围：全项目流程（核心服务层 `src/mock/flow.js`、各业务域种子、路由/权限、关键页面、`scripts/verify-*.mjs`）
> 目的：评估流程是否合理、是否完整闭环，列出可修改问题与待补充环节，防止进度丢失。

---

## 一、总体评价

纯前端（Vue 3 + Element Plus + Pinia）大宗物流平台演示，全部业务逻辑下沉到 mock 服务层（`src/mock/flow.js`，约 2680 行）。架构成熟度高于一般 AI 生成项目，已具备：

| 维度 | 现状 |
|---|---|
| 权限 | RBAC 菜单级 + 按钮级 + 服务层单点校验 + 行级数据权限（默认拒绝） |
| 状态机 | 调度单 `待装货→装货中→在途→卸货中→已完成` + 异常分支，含守卫 |
| 联动回卷 | 调度→计划→合同进度自动对齐；资源占用/释放 |
| 并发 | 车辆/司机乐观锁（version + 提交前二次校验） |
| 定时任务 | 围栏事件 / GPS 遥测 / 逾期校准（独立于页面生命周期） |
| 结算闭环 | 生成→三方对账→客户确认/异议→确认结算→收款/预付/银行核销→逾期 |
| 发票 | 开具 / 红冲 / 金额陈旧标记（票款一致拦截） |
| 安全 | 事故 / 培训 / 车辆检查 / 年检驾照过期拦截 |
| 门户/司机端 | 需求→合同、对账确认/异议、接单/扫码/电子签收/收入 |
| 登录安全 | 验证码 + 密码哈希 + 失败锁定 |
| 其他 | 审计日志、电子单证归档、5 类报表、Excel 导入、消息定向+免打扰、localStorage 持久化 |

**主链路（合同→计划→调度→执行→异常→结算→开票→收款→单证→报表）完整闭环**，且 `scripts/verify-flow.mjs`（服务层冒烟）与 `scripts/verify-ui.mjs`（19 组 E2E）覆盖较全。

## 二、业务闭环缺口（缺失环节）

按对闭环正确性的影响排序。

### P0 — 影响数据/流程正确性

1. **收款无冲正/退款**：`recordPayment`（flow.js:1277）只增不减，误登记收款无法撤销，`paidAmount` 无回退路径，也无退款流程。
2. **派车非事务（部分成功）**：`createDispatches`（flow.js:920-928）循环建单，第 M 张 `validateResourceCommit` 失败时直接 return，前 M-1 张调度单残留、计划状态不更新。可用车辆数 < 请求派车数时会留下"半套"调度单。
3. **异常补扣未失效客户确认**：`closeException`（flow.js:723）在已结算账单补扣损失、改发票金额（触发红冲重开）时，未清除 `s.customerConfirmed` 与 `s.reconciliation`——客户对原金额的确认逻辑上已失效，但流程不要求重新确认。
4. **磅单不可更正**：磅单无修改/复磅流程，净重错了无法从源头修正（补录仅针对缺失），对账差异无法溯源处理。

### P1 — 补全业务闭环（当前是"单边闭环"）

5. **司机/外协车付费缺失**：`driverIncomeOf`（flow.js:1575）算了趟次收入，但没有向司机/外协车主付款的流程。**收入侧闭环了，成本侧没闭环**。
6. **调度单无取消/改派**：下发后车辆故障或客户改期，无法取消或改派调度单（只有计划可取消且仅限待执行）。
7. **逾期无催收**：逾期仅状态标记，无催款记录、付款提醒、催收工作流。
8. **外协车/场站费用未单独结算**：车辆有 `owner: 自有/外协`，装卸费已并入账单，但外协运费、场站作业费无独立结算对象。
9. **发票双入口口径不一**：`issueInvoice`（flow.js:2064，结算详情，新建）与 `issueInvoiceRow`（flow.js:2089，发票页，更新 pending）两条路径；运行时新账单无 pending 记录，后者实际只对种子/红冲重开生效，建议统一。

### P2 — 增强真实度

10. **进磅净重 = 调度量（非实际过磅）**：`doConfirmLoad`（flow.js:528）直接 `pushWeighing(d,'进磅',d.quantity)`，导致损耗率恒为固定 1.5%，且**对账"差异"恒为 0**——`buildReconciliation`（flow.js:1144）的差异检测（`RECONCILE_TOLERANCE`）在正常流程里是死代码，环节 2 客户异议流程实际跑不起来。
11. **报表口径不一致**：`costReport`（report.js:120）收入用 `d.fee`（调度量×单价），结算却按出磅净重；`customerReport`（report.js:54）授信占用未扣预付款，与 `creditCheck`（flow.js:1391）口径不一致。
12. **单证类型不全**：归档只有磅单/签收单/发票；调度单（可打印但未归档）、对账单、质检报告未纳入。
13. **缺运价管理**：单价合同手工填，无线路运价表/调价。
14. **异常/审批无升级与超时提醒**：异常单一直 pending 直到人工受理，无升级机制；合同审批无超时提醒。
15. **缺保险环节**：事故后无投保/理赔/责任认定。
16. **仓储缺成本/盘点/调拨**：库存只有数量，无成本、无盘点单、无多仓调拨。

## 三、架构 / 工程问题

1. **operator 默认"平台管理员"（默认放行）**：flow.js:58 未登录态按最高权限放行，与 RBAC"默认拒绝"原则相悖。浏览器登录守卫保证了 `setOperator`，风险有限，但设计上是 default-allow。
2. **前端即服务层**：所有校验在客户端，整个 `db` 在浏览器里，真实安全需后端承接（注释已承认是演示限制；对接后端时本模块函数即 endpoint 校验逻辑——这点设计正确）。
3. **`db.logs` / `db.messages` 无上限**：持续增长会撑爆 localStorage 5MB 配额（`saveDb` 静默忽略），长期运行有丢快照风险。
4. **无单元测试 / 无 CI**：只有冒烟 + E2E；`package.json` 无 CI 配置。
5. **无全局错误处理**：未设置 `app.config.errorHandler`。
6. **持久化无并发保护**：多标签页同时编辑互相覆盖（last-write-wins）。

## 四、建议补充环节（落地优先级）

| 优先级 | 环节 | 说明 |
|---|---|---|
| **P0** | 收款冲正/退款 | 误收款可撤销，`paidAmount` 可回退，留审计 |
| **P0** | 派车事务化 | 全成或全滚（先校验全部资源再统一落库） |
| **P0** | 异常补扣失效客户确认 | 改额后清 `customerConfirmed`，要求重新对账确认 |
| **P0** | 磅单更正/复磅 | 差异可从源头修正并触发重新对账 |
| **P1** | 司机/外协付费 | 成本侧闭环（应付趟次费→付款→核销） |
| **P1** | 调度单取消/改派 | 执行前可取消或换车换司机 |
| **P1** | 逾期催收 | 催款记录 + 提醒 + 状态流转 |
| **P1** | 统一发票入口 | 收敛为单一开具路径 |
| **P2** | 进磅实际过磅 | 随机损耗，让对账差异/异议流程真实可跑 |
| **P2** | 报表口径对齐 | 收入按出磅净重、授信扣预付款 |
| **P2** | 单证扩充 | 调度单/对账单/质检报告归档 |
| **P2** | 运价表 + 异常升级 + 保险 | 增强真实度 |
| **P3** | 工程加固 | operator 默认拒绝、logs/messages 上限、CI+单测、全局错误处理 |

## 五、结论

**流程合理且主链路闭环完整**，架构分层（视图只读、写操作下沉服务层、RBAC 单点校验、乐观锁、定时任务）在纯前端演示里做得规范，校验脚本覆盖到位。主要短板：

- **成本侧不闭环**（只收不付，司机/外协/场站费用无结算）；
- **几个 P0 级正确性缺口**（收款不可逆、派车非事务、异常补扣不失效确认、磅单不可更正）；
- **对账差异流程实际跑不起来**（进磅=调度量导致差异恒 0）；
- **工程侧**（默认放行、无上限日志、无 CI/单测）。

定位判断：若目标是"演示/方案展示"，现状已足够；若要往**可落地的业务系统**演进，先补 P0 四项正确性缺口，再补 P1 成本侧闭环。
